# Visual exploration

Use this procedure when the task actually requires a new visual direction. Read only the source material relevant to the chosen scope.

## Ground the direction

Inspect the reference image or website, current UI if present, and the brief. Record a URL or file identity, observation date, relevant page/state, and adopted characteristics. If access fails, record that and work only from information actually available; do not claim to have analyzed the reference.

Separate these decisions:

| Decision | Useful evidence |
| --- | --- |
| Composition and density | The user's primary task, information priority, real content volume |
| Typography and hierarchy | Existing product foundations, language, label and value lengths |
| Color and emphasis | Brand references, status meaning, priority of user actions |
| Spacing and containment | Group relationships, interaction targets, viewport and container |
| Imagery and decoration | Their actual role in the product, reference characteristics |

Do not translate a reference into a pile of fashionable visual effects. Explain how each substantial choice supports this product. Retain established tokens and components in brownfield work unless changing them is part of the requested scope.

## Plan comparable candidates

Default to two directions with a meaningful difference in composition, information density, hierarchy, or visual character. A hue swap is insufficient. Keep representative content and scenario consistent enough for the user to compare the choices. When the user already chose a direction, make one concrete proposal and record the reason.

For a single page, show its main task at the intended dimensions. For a feature or multi-page journey, show a representative page plus the additional screen/state images needed to expose material visual decisions across the journey. Include a narrow-container example when a webview or sidepanel is in scope. Record dimensions and content assumptions beside each output.

Use plausible names, labels, dates, counts, long titles, and dense rows from the product domain. These are synthetic fixtures. Do not imply they are real customer data or a verified backend contract.

Immediately before producing the planned candidates, apply [model routing](../../ui-ux/references/model-routing.md). Resolve the scoped model/effort and generator decision, approval when required, and actual execution settings; reuse an unchanged decision already established by the router or style skill. Preparation above does not authorize generation before this boundary.

Then use an available image-generation capability for generated raster visuals. If unavailable, an actual static PNG/SVG layout render can satisfy the image artifact requirement when clearly labeled with its method and limitations. Preview the output to check the intended layout and content. A rendering failure remains a missing artifact.

## Make approval concrete

Use [visual decisions](../templates/visual-decisions.md) for the accompanying note. Present the actual candidates, their meaningful differences, and your recommendation grounded in the brief. Approval concerns the named candidate's visual intent and specified scope, not all generated labels, business behavior, or production feasibility.

Record the approval using the shared [approval template](../../ui-ux/templates/approvals.md). An already explicit user approval can be recorded directly when the artifact and scope are unambiguous; do not make the user repeat it. Silence, elapsed time, or a generic implementation request does not approve a new candidate. If the user revises a material choice, create the next revision, preserve the approved version, and reopen only the affected decision.

Hand off the selected images and written foundations. Approximate image typography, fabricated data, or accidental image elements must not override explicit tokens, authorization rules, validation, payloads, or domain transitions.
