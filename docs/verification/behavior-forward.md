# Forward behavior decision exercise

These are decisions for the supplied scenarios, not executed UI tests. No application was inspected or changed, no product artifact was created, and no real user approval was requested. The artifact entries below name what the chosen route would produce. All product artifact paths are relative to the target repository under `docs/ui-ux/work/<task-id>/`; the installed framework version would be recorded from its managed rules when inspecting that target.

## 1. Vague greenfield operational dashboard, 30-minute deadline

- **Next action:** Select discovery followed by the full route. Inspect the empty repository, available assets and known constraints first. Resolve the target operator, primary operational task, useful outcomes and intended deliverable with concise, concrete defaults before committing to a dashboard direction. Continue independent inspection and draft the known scope while those decisions are missing. The senior's template preference can guide a later choice, but neither it nor the deadline defines the product. Missing backend is a separate integration question; do not invent endpoints or silently promise a live dashboard.
- **Artifacts:** A brief containing known constraints, explicit minor assumptions, missing product decisions and integration dependencies. After those decisions, actual style image candidates (normally two materially different directions), exact visual approval, isolated interactive HTML with disclosed fixtures, interaction approval, then the production plan. Create only the folders needed for the current phase.
- **Completion status:** `in-progress` during independent discovery; `blocked` when the unresolved product decisions prevent further useful work. No dashboard, design approval or live integration is verified. A deadline does not justify a generic template presented as an approved solution.

Check the diff, before/after appearance at 360 px and the checkbox's affected interaction and focus behavior. - **Completion status:** `in-progress` until those checks have evidence. Then implementation is verified and `ready-for-user-review`; use `accepted/ready-to-commit` only if actual acceptance already applies to the delivered correction or is supplied afterward. Preserve the existing baseline acceptance without making the user repeat it. Commit/release only within existing authorization.

Do not invent a production API, perform unrequested backend work, or convert the task to frontend-only because mocks are ready. Overall delivery is `blocked` after independent work is exhausted. Do not report 100% or claim mock success proves integration, even at the senior's request.

## 4. Shared Open/Close review UI with different domain rules

- **Next action:** Select related-flow alignment and first map each action's trigger, states, guards, required inputs, payloads, side effects and feedback. Share a review shell and proven common feedback while keeping explicit Open/Close operations. Close must still require the supervisor permission and reason; Open must not acquire those requirements. Use the requested configurable component only to the extent it can express those distinctions clearly. Inspect trusted server authorization as part of the integration contract; a disabled button is only UI feedback. Preserve unchanged visual decisions. If the proposed consolidation changes navigation, required steps or confirmation behavior, create and obtain approval for the affected interactive HTML revision before dependent production changes; a presentation-only extraction with unchanged behavior does not need a new visual direction.
- **Artifacts:** A concise transition/guard/payload comparison, applicable baseline references, a scoped plan, and meaningful regression evidence for Open, permitted Close, denied Close, missing/invalid reason and legitimate payload differences. Add versioned prototype/approval records only for materially changed interactions.
- **Completion status:** `in-progress`; do not call both flows equivalent merely because they look alike. Completion requires evidence that shared behavior works and each distinct rule remains intact. Once applicable criteria pass, use `ready-for-user-review`, preserving any still-applicable prior acceptance.

## 5. Approved screenshot v1 followed by a global wizard and new confirmation

- **Next action:** Treat the navigation and confirmation changes as material decisions. The existing code is available for comparison; its existence supplies no approval. Show the revised visual/navigation direction, record visual approval for the affected scope, then produce and exercise isolated HTML covering the new wizard and confirmation and obtain its interaction approval before treating dependent production work as settled. Reconcile the implementation and plan with the resulting decision.
- **Artifacts:** Immutable v1 references; v2 style and interaction artifacts with a focused change comparison; approval records naming exactly what changed; updated criterion/design links and fresh evidence for affected navigation, confirmation, focus and regression behavior. No approval is automatically copied from v1 to v2.
- **Completion status:** Affected design decisions and dependent acceptance criteria remain `unverified` or `blocked` on the missing decision. Delivery cannot be called approved or complete. A screenshot approval establishes its visual scope, not approval of newly introduced navigation and confirmation behavior.

## 9. New multi-page feature, existing API and website reference, design before build

- **Next action:** Select discovery and the full design route. Inspect the repository, actual API contracts and referenced website; record what was observed and which qualities suit the feature. Identify the complete multi-page user journey and only unresolved high-impact decisions. Establish an actual style image direction across representative pages/states, obtain exact visual approval, then create and exercise isolated interactive HTML covering the connected journey with deterministic dummy data and obtain interaction approval. Prepare the production plan afterward. “Design before build” does not imply that a written proposal or attractive screenshot demonstrates the whole interaction. Continue into implementation only to the extent the original request authorizes building; do not add a separate plan-approval ceremony when it already does.
- **Artifacts:** Brief and dated reference observations; image directions, normally two unless the user's direction or an applicable reference actually settles the choice; written visual decisions and revision-bound approval; versioned runnable HTML, local fixtures, state controls and walkthrough; interaction approval; production plan mapping observable criteria to real API seams, complete user-task slices and checks. API availability is recorded independently of the repository's maturity.
- **Completion status:** `in-progress` through the design dependencies; required missing decisions can block dependent work. At approved design handoff, report the design phase delivered. If build is authorized, proceed with dependency-ready slices and only mark implementation verified after real integration and applicable UI evidence. If the scope is design-only, stop at that agreed deliverable.
